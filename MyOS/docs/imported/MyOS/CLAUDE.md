## 2. What This Project Is

Yfitops OS is a sovereign, privacy-first desktop operating system shell. It is not a web app, not a productivity tool SaaS, and not a hobby project. It is a real operating environment built on the principle that the user owns their machine, their data, and their identity.

Every architectural decision must be evaluated against these five values, in priority order:

1. **User sovereignty** — the user controls everything, always
2. **Privacy by default** — no telemetry, no outbound calls, no fingerprinting
3. **Local-first** — the system must function with no internet connection
4. **Modularity** — every component must be independently replaceable
5. **Stability** — a working system is more valuable than a perfect rewrite

## 3. Technology Rules

### Backend (Rust / Tauri v2)
- All system logic lives in Rust. No Node.js backend going forward.
- Use `tauri-specta` to generate TypeScript bindings from Rust command signatures. The generated `bindings.ts` is the contract — never type it manually.
- State lives in `AppState` (see `src-tauri/src/state.rs`). Use `Arc<Mutex<T>>` for shared mutable state.
- Database is SQLite via `tauri-plugin-sql` (sqlx backend). All queries use prepared statements. No string interpolation in SQL. Ever.
- Use `sysinfo` crate for system health. Never shell out for system stats.
- Exec commands use a strict whitelist. Never interpolate user input into shell calls.

### Frontend (HTML / CSS / JS)
- Vanilla HTML, CSS, and JavaScript only. No frameworks unless I explicitly approve them in writing.
- No `eval()`. No `innerHTML` with API-sourced data. Use `textContent` or `createElement`.
- All API calls go through `src/yos-api.ts` which wraps the generated Tauri bindings. No direct `invoke()` calls in module HTML.
- Every module loads `shared/theme.css` and `shared/titlebar.html`. No module defines its own colour tokens.
- CSS variables are defined in `shared/theme.css`. Never hardcode `#00ff88` or any other colour in a module.

## 4. AI Behaviour Rules

### Before touching code
1. Read the relevant `SPEC.md` for the module being modified.
2. Read `security/PERMISSION_MANIFEST.md` to understand what the module is allowed to do.
3. Read `security/THREAT_MODEL.md` to understand what not to break.
4. State your understanding of the current implementation before proposing changes.

### When proposing changes
- Explain the root cause before proposing the fix.
- Prefer atomic, targeted changes over refactors.
- Never rewrite a working system to make it "cleaner" without explicit instruction.
- If a change affects the permission model, call it out explicitly.
- If a change requires a database migration, write the migration SQL.
- If a change adds a new Rust command, update `bindings.ts` generation notes.

### When writing code
- All Rust commands include a permission guard check as the first operation.
- All SQL queries use prepared statements.
- All user-facing strings are kept in a constants file, not inline.
- All new modules include a `ModuleManifest` with minimum required permissions.
- Error messages are descriptive but never expose internal paths or system details.

### When in doubt
- Ask one clarifying question. Not multiple. Not zero.
- Default to the more restrictive option on security questions.
- Default to the simpler implementation on architecture questions.
- Do not make assumptions about the deployment environment.

## 5. What Claude Must Never Do

| Action | Reason |
|--------|--------|
| Add telemetry, analytics, or crash reporters | Violates core privacy principle |
| Suggest cloud sync, cloud backup, or API services | Violates local-first principle |
| Use `eval()` in any frontend code | Security — XSS vector |
| Interpolate user input into shell commands | Security — command injection |
| Expand the exec whitelist without explicit approval | Security — privilege escalation |
| Rewrite a working module without approval | Stability — breaks deployment |
| Add frontend frameworks without approval | Architecture — violates vanilla-JS rule |
| Remove or bypass the permission guard | Security — destroys module isolation |
| Hard-code colour values in module CSS | Architecture — breaks theming system |
| Write SQL with string concatenation | Security — SQL injection |

## 6. Commit and Change Protocol

All persistent code changes must be reflected in `import.txt` (the master deployment file) before they are considered complete. A change that exists only in source files but not in `import.txt` is an incomplete change.

Commit message format:
```
<type>(<scope>): <short description>

Types: feat, fix, refactor, docs, security, chore
Scope: terminal, files, notes, health, settings, packages, shell, security, docs

Examples:
feat(notes): add full-text search via SQLite FTS5
security(exec): restrict whitelist to 10 approved commands
fix(titlebar): traffic light buttons not firing on Linux
docs(decisions): ADR-003 for SQLite migration choice
```

## 8. Definitions

| Term | Meaning |
|------|---------|
| Module | A standalone HTML page loaded in a native Tauri window |
| Command | A Rust function exposed to the frontend via `#[tauri::command]` |
| Manifest | A `ModuleManifest` struct defining a module's declared permissions |
| Permission | A capability enum value (`ExecWrite`, `FileRead`, etc.) |
| Sovereign Mode | Session with full SQLite persistence |
| Amnesic Mode | Session with in-memory SQLite only, wipes on exit |
| .yops | The Yfitops package format (JSON manifest + zipped module) |
| Guard | The `PermissionGuard::assert()` call at the top of every command |
| import.txt | The master deployment file — source of truth for all system state |
