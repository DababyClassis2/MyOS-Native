## 1. Executive Summary
MyOS is a sovereign, privacy-first desktop shell designed to run as a native application on a minimal Linux base (Alpine musl). It replaces the traditional desktop environment with a compiled Rust gateway and an isolated, permission-gated WebView interface.

---

## 2. Design Principles
1. **User Sovereignty:** The user owns the data, the permissions, and the execution flow.
2. **Privacy by Default:** Zero telemetry. Local-first execution.
3. **Local-First:** All core services (Notes, Files, Terminal) function without an internet connection.
4. **Sandboxed Security:** Every module is isolated and must request capabilities via a Permission Guard.
5. **Amnesic Capability:** Support for a "Live" mode where all session data is wiped on exit (In-memory SQLite).

---

## 3. System Architecture

### Layer 1: OS Foundation (Alpine Linux)
*   **Kernel:** Linux (musl libc).
*   **Role:** Handles hardware, drivers, and basic process scheduling.
*   **Deployment Target:** Bare-metal boot with MyOS as the `init` or primary shell.

### Layer 2: The Gateway (Rust / Tauri)
*   **Role:** The "Brain" of the OS. Manages window spawning, system bridges, and security.
*   **State Management:** `AppState` struct managed via `Arc<Mutex<T>>`, containing the DB pool, Permission Guard, and Workspace state.

### Layer 3: Data Layer (SQLite)
*   **Persistence:** `yfitops.db` (on-disk) or `:memory:` (Amnesic).
*   **Key Tables:**
    *   `settings`: Profile-scoped key/value pairs.
    *   `audit_log`: Immutable record of every system action.
    *   `notes`: Full-text searchable (FTS5) user notes.
    *   `packages`: Manifests for installed `.yops` modules.
    *   `workspace_state`: Persisted window positions and active modules.

### Layer 4: User Interface (HTML/CSS/JS)
*   **Technology:** Vanilla JS, CSS Variables, and HTML5.
*   **Structure:** 
    *   `index.html`: The main Desktop Shell (Dock, Top Bar).
    *   `modules/`: Isolated pages for Terminal, Files, Settings, etc.

## 4. Security Model

### 4.1 Permission Guard
Every Rust command starts with a capability check.
*   **Logic:** `state.permission_guard.assert_capability(module_id, permission)`
*   **Enforcement:** If a module (e.g., `notes`) tries to call a command it doesn't have (e.g., `ExecCommand`), the gateway returns a `Permission Denied` error.

### 4.2 Audit Logging
An immutable trail of every sensitive action.
*   **Event Types:** `EXEC_START`, `READ_FILE`, `SET_SETTING`, `PERMISSION_DENIED`, etc.
*   **Schema:** `(timestamp, module_id, action, detail, severity, profile_id)`.

### 4.3 Sandbox Root
The `files` module is restricted to a specific root directory (e.g., `D:/My-Os-Project`). Path traversal above this root is blocked by the `assert_path_in_sandbox` logic.

## 6. IPC Interface (Tauri Commands)

The Frontend communicates with the Backend using `invoke()` calls. All commands follow a standard Result pattern:

```typescript
// Example: Executing a command
const output = await invoke('exec_command', { 
  moduleId: 'terminal', 
  command: 'ls' 
});
```
